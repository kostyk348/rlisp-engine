# Бенчмарки

Правила этого файла: только числа из реальных запусков, с точным указанием
окружения; метки каждого числа говорят, что именно мерялось.

## Окружение замеров

- **Песочница (headless, без GPU-адаптера)** — здесь записаны все числа ниже:
  Linux x86_64 (контейнер, kernel 5.10), rustc 1.83.0, `cargo build
  --release` (opt-level=3, lto, codegen-units=1), CPU: серверный x86_64
  (VPS-класс, AVX2 есть, AVX-512 не используется — см. `build.rs`), экран
  320×240, режим headless (без вывода кадров).
- **GPU-железо** — недоступно в песочнице. Все wgpu-числа ниже — это
  программный растр после честного фолбэка (`--wgpu` печатает
  «wgpu-адаптер недоступен» и откатывается), либо помечены как «ожидает
  железа».

## Этап 3: JIT числовых ядер — песочница, реальный запуск 2026-11-09

Окружение: то же (Linux x86_64, kernel 5.10, rustc 1.83.0, release
opt-level=3+lto, CPU VPS-класса AVX2; диспетчеризация SIMD калибруется в
SSE2). Сборка: `cargo build --release --features jit`.

**Сцена помечена честно**: замеряется ВЫЗОВ маленькой числовой лямбды
`(lambda (x y) (if (< x y) (+ (* x x) (* y 2.0)) (- (* x y) (/ x y))))`
в цикле из Rust-хоста (ядро как в игровых update-функциях: арифметика +
сравнение + if + деление). Это НЕ «вся игра быстрее в N раз»: ускоряется
вызов числовой лямбды на горячем пути; код кадра (нативы HAL) не меняется.

| Путь | 200 000 вызовов | нс/вызов |
|---|---|---|
| interp (`apply_lambda`: bind_params + eval каждого узла) | 459.3 мс | 2296.5 |
| JIT (`apply`: гард арности/типов + нативный вызов x86-64) | 9.4 мс | 46.8 |

**Ускорение 49.07× — критерий этапа (≥5×) выполнен.** Контрольная сумма
результатов 201261.3303 одинакова для обоих путей (кроме Int/Float
представления: JIT возвращает f64). Повторные прогоны в этой песочнице дают
33–49× (шум VPS-класса; оба значения много выше критерия 5×). Команда:
`--bench` (секция «бенч JIT числовых ядер»).

## Этап 3: SIMD-токенизатор — песочница, реальный запуск 2026-11-09

Корпус: 13 файлов `assets/lisp/*.lisp`, 59169 байт (реальные исходы движка
с русскими комментариями), 200 прогонов. До замера — обязательная взаимная
сверка AST scalar-vs-simd: OK.

| Замер | scalar (старый путь) | SIMD | ускорение | Критерий |
|---|---|---|---|---|
| парсер end-to-end (parse_program) | 210.8 мс (56 МБ/с) | 197.0 мс (60 МБ/с) | **1.07×** | ≥3× — **НЕ выполнен** |
| лексический скан отдельно (без построения Value) | 62.3 мс (190 МБ/с) | 66.3 мс (179 МБ/с) | **0.94×** | — |

**Критерий парсер ≥3× не достигнут — числа настоящие, без подгонки.** Разбор:

1. Парсер аллокационно упирается: String на каждый атом (`parse_atom`) и
   построение Value занимают подавляющую часть времени и идентичны для обоих
   путей. Быстрый путь в `parse_atom` (не-числовой атом → сразу Sym, без
   попыток parse::<i64>/f64) ускорил оба пути одинаково.
2. Много-классовый скан (11 pcmpeqb + 3 movemask на 16 байт) на лексемах
   длиной 3–8 байт проигрывает посимвольному: memchr-сканеры выигрывают на
   длинных прогонах одного класса, а лексер Lisp останавливается каждые
   несколько байт; плюс per-call оверхед скана (наборы-векторы, пролог).

Лечение на следующие этапы: интернирование символов / bump-аллокация атомов
(пол времени), pshufb-классификация байтов (одна таблица на 16 байт вместо
11 сравнений), скан всего файла одним проходом с последующим разбором по
списку позиций. Старый reader сохранён как эталон и fallback — взаимная
сверка AST остаётся частью тестов и `--bench-parse`.

## Этап 7: 3D-шейдинг (материалы) — песочница, реальные запуски 2026-11-09

Окружение: то же (Linux x86_64, kernel 5.10, rustc 1.83.0, release
opt-level=3+lto, CPU VPS-класса AVX2, headless). Команда: `--bench`
(секция «бенчмарк 3D-шейдинга», `bench_3d_shading` в `src/main.rs`).

**Сцена помечена честно**: батч-вершинник, 100 текстурных квадов 6×6
(билборды с альфа-прорезями, экранный охват ~100%), экран 320×240,
z-буфер очищается каждый кадр (как `gpu3d-clear`), один и тот же кадр для
всех конфигураций — разница только в состоянии материалов. Замеряется
чистая стоимость растра без интерпретатора (прямые вызовы Rust-HAL),
100 кадров на конфигурацию, перед замером — прогрев.

Прогон (последний, абс. значения):

| Конфигурация | мс/кадр | дельта к базе |
|---|---|---|
| Lambert, материалы выкл (база этапа 6) | 6.85 | — |
| + alpha-test 0.5 (cutout 25% текселей) | 7.12 | +3.9% |
| + блик Blinn-Phong (spec 0.6, shininess 48) | 10.03 | +46.4% |
| + туман (density 0.06, глубина 1/w) | 7.85 | +14.6% |
| весь материал (alpha + блик + туман) | 10.91 | +59.3% |

Разброс по 4 запускам: alpha-test +3.4…+4.0%, блик +44.9…+46.8%,
туман +13.3…+15.0%, весь материал +58.6…+61.8%.

Разбор: кадр доминирует перспектива-корректная растеризация (клиппинг,
edge-функции по bbox ~1 млн пикселей с овердроу). Блик прибавляет
per-pixel нормализацию векторов и `powf` на каждом z-проходе (~78 тыс.
пикселей) — +45%; туман — один `exp` на z-проход — +15%; alpha-test почти
нейтрален: branch на тексель компенсируется отбрасыванием 25% записей
(за дырами не пишутся ни цвет, ни z). Всё вместе — +60% к базовому кадру;
это цена материала, а не регресс: база измеряет тот же кадр без
материалов, и при выключенных фичах путь пиксельно совпадает с этапом 6
(ноль накладных расходов на дефолтной конфигурации).

## wgpu-бэкенд — ожидает GPU-железа

Критерий роадмапа «`--wgpu` кратно быстрее» **не проверен: в песочнице нет
GPU-адаптера**. Что уже проверено без железа:

- `cargo check --features wgpu` / `cargo test --features wgpu` — зелёные на
  rustc 1.83 (wgpu 0.20.1, MSRV 1.75);
- `--wgpu` без адаптера печатает
  «wgpu-адаптер недоступен (headless/CI/VM без GPU…) — откат на программный
  растр» и продолжает работать; все smoke-проверки зелёные;
- `--bench --wgpu` в такой среде печатает «wgpu-адаптер недоступен» и
  выходит с кодом 0.

На машине с адаптером (Vulkan/Metal/DX12) `--bench --wgpu` выдаёт разбивку:
`submit` (запись+отправка команд GPU) и `readback` (copy+map+композит
CPU←GPU) по отдельности, плюс тот же Lisp-замер. Readback — осознанная
стоимость этапа 1: движок headless, кадр всегда возвращается в `Hal::fb`
для PNG/ASCII/редактора; на железе ожидаемая картина — submit+readback
сопоставимы по цене с софт-растеризацией лишь на слабых GPU, а выигрыш
появляется на сложных сценах (большие fill-rect/blit площади) — проверится
на этапе 5 (3D-игра на wgpu).
